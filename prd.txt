# Ticketing App with Time Tracking - Product Requirements Document (PRD)

## 📋 Document Information
- **Product Name**: Ticketing App with Time Tracking
- **Version**: 1.0 (MVP)
- **Date**: [Current Date]
- **Author**: Engineering Team
- **Status**: Draft

## 🎯 Executive Summary

### Product Vision
PulseTrack is a comprehensive SaaS project management platform that combines ticketing, time tracking, and billing into one seamless solution. Designed for teams who need to manage projects efficiently while tracking billable hours and generating professional reports for clients.

### Target Users
- **Primary**: Software development agencies and consultancies
- **Secondary**: Freelancers and small project teams
- **Tertiary**: Enterprise teams requiring detailed time tracking and billing

### Success Criteria
- Users can create and manage projects within 30 seconds
- Ticket creation takes less than 1 minute
- Time tracking is accurate and easy to use
- Dashboard provides actionable insights
- System handles 100+ concurrent users

## 🛠️ Technical Stack
- **Frontend**: Next.js 14+ (App Router)
- **Backend**: Supabase (PostgreSQL + Auth + Real-time)
- **State Management**: Zustand
- **UI Framework**: shadcn/ui + Tailwind CSS
- **Language**: TypeScript
- **Deployment**: Vercel

## 🏢 Multi-Tenancy Structure
- The system is multi-tenant: each company's data is isolated.
- Users, projects, and tickets are always scoped to a company.

## 📊 MVP Scope

### ✅ Included in MVP
- User authentication and basic profile management
- Project creation and management
- Ticket creation, assignment, and status management
- Basic time tracking (start/stop timer)
- Simple dashboard with key metrics
- Basic search and filtering
- User role management (Admin, Manager, User)
- **Comprehensive billing system with user role access**
- **Personal billing period generation for users**
- **Professional invoice generation and payment tracking**

### ❌ Excluded from MVP (Future Releases)

## 7. Billing & Time Reports

### 7.1 Billing Periods Management
**Requirement**: Companies can define and manage billing periods for time tracking reports with user self-service capabilities.

**Functional Requirements**:
- Companies can create billing periods (weekly, bi-monthly, monthly)
- Billing periods have start date, end date, and status
- Users can view active and past billing periods
- Time entries are automatically grouped by billing period
- **Admin Management**: Company admins can manage all billing periods
- **User Self-Service**: Regular users can generate personal billing periods for company review
- **Role-Based Access**: Users access "My Billing Periods" while admins access "Billing Periods"
- **Personal Billing Workflow**: User-generated periods are sent to company for approval

**Technical Requirements**:
- Billing periods table with company scoping
- Automatic time entry aggregation by period
- Efficient querying for large time entry datasets
- Period overlap validation
- **Role-Based API Permissions**: Action-specific permission checks for user vs admin operations
- **User Data Filtering**: Multi-query approach for user-specific billing period visibility
- **User Identification in Notes**: Admin-created periods include user ID in notes for targeting
- **API Endpoint Security**: User validation for personal billing period generation

**Data Model**:
```sql
billing_periods {
  id: uuid (primary key)
  company_id: uuid (foreign key to companies)
  name: text (required, e.g., "Week 26 2025", "January 2025")
  start_date: date (required)
  end_date: date (required)
  frequency: enum ('weekly', 'bi_monthly', 'monthly')
  status: enum ('active', 'closed', 'draft')
  created_by: uuid (foreign key to users)
  created_at: timestamp
  updated_at: timestamp
}
```

**Acceptance Criteria**:
- [x] Admin can create new billing periods
- [x] Billing periods cannot overlap for the same company
- [x] Users can view current and past billing periods
- [x] Time entries are automatically associated with periods
- [x] Period status can be changed (draft → active → closed)
- [x] **Users can generate personal billing periods for themselves**
- [x] **Users see only their own billing data (self-created + admin-created for them)**
- [x] **Admin-created user periods are visible to target users via notes field**
- [x] **API endpoints support both admin and user billing period creation**
- [x] **Role-based filtering ensures data isolation between users**

### 7.1.1 User Role Billing Access
**Requirement**: Regular users can access billing functionality with appropriate restrictions and self-service capabilities.

**Functional Requirements**:
- **Tab Access**: Users can access "My Payments" and "My Billing Periods" tabs
- **Personal Data View**: Users see only their own payment and billing data
- **Self-Service Generation**: Users can create personal billing periods for approval
- **Custom Date Ranges**: Users can specify custom date ranges for billing periods
- **Admin Oversight**: Admin-created billing periods for users are visible to target users

**Technical Implementation**:
- **Multi-Query Filtering**: Separate queries for user-created and admin-targeted periods
- **Pattern Matching**: User ID matching in billing period notes field for admin-created periods
- **API Permission Model**: Action-specific validation (users can only generate for themselves)
- **UI Role Adaptation**: Dynamic tab labels and functionality based on user role

**Data Flow**:
1. User generates personal billing period → Saved with user as creator
2. Admin generates period for user → User ID included in notes field
3. User views billing periods → System queries both user-created and admin-targeted periods
4. Results combined and deduplicated for unified user experience

**Acceptance Criteria**:
- [x] **Users can access payments and billing periods tabs**
- [x] **Users see role-appropriate tab labels ("My Payments" vs "Payments")**
- [x] **Users can generate personal billing periods with custom date ranges**
- [x] **User billing data is properly filtered (own data only)**
- [x] **Admin-created user periods are visible to target users**
- [x] **API endpoints validate user permissions for personal billing operations**

**Data Model**:
```sql
billing_rates {

  currency: text (default 'USD')
  effective_from: date (required)
  effective_to: date (nullable)
  created_by: uuid (foreign key to users)
  created_at: timestamp
}
```

**Acceptance Criteria**:
- [ ] Admin can set company default rates
- [ ] Admin can set user-specific rates
- [ ] Admin can set project-specific rates
- [ ] Rate changes are tracked with effective dates
- [ ] Billing calculations use correct historical rates
